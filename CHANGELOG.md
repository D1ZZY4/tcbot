### Added

- **An exhausted enforcement failure can be re-driven by an operator** (`tcbot/database/enforcement_db.py`, `tcbot/modules/maintenance.py`, `i18n/en-US/maintenance.toml`, `i18n/id-ID/maintenance.toml`): the ledger retried a transient group failure three times and then left the target terminal, so the only way back was filing a second moderation decision. `/tcrepair` now lists the queued, running, partial, and failed runs with their applied, failed, and exhausted counts, and `/tcrepair retry <run_id> [chat_id]` returns the existing run, or one requested group, to the worker. Behavior changes: staff can repair a failed delivery without creating a new verdict; a run already owned by the worker or a cancelled run is refused.

- **The connect flow reports the new Welcome Messages admin right** (`tcbot/modules/helper/pipelines/connected_flow.py`, `i18n/en-US/connecting.toml`, `i18n/id-ID/connecting.toml`, `tests/test_complete_join.py`): Bot API 10.3 added `can_send_welcome_messages`, but PTB 22.8 does not expose it and Bot API has no method that sets the native welcome message. The bot reads the grant through the public raw-request escape hatch and appends a note to the connect success message when the grant is explicitly missing. A server that omits the field and a failed probe stay silent. Behavior changes: the permission is audited, never required, and it does not block a connection; the native welcome content still has to be configured manually in the Telegram app.

- **Ban, mute, and warn application now has a durable per-group ledger** (`tcbot/database/bans_db/_writes.py`, `tcbot/database/mutes_db.py`, `tcbot/database/enforcement_db.py`, `tcbot/enforcement_worker.py`, `tcbot/modules/helper/pipelines/ban_flow.py`, `mute_flow.py`, `warn_flow.py`): a manual or automatic ban and a mute queue an `apply` run with their decision, and Telegram delivery is recorded per group. A failed group is retried by the scheduled worker instead of disappearing with the one-shot fan-out. Behavior changes: the ban and mute summaries report the per-group run outcome, and a failed delivery is retried automatically.

- **The retention contract now runs** (`tcbot/database/scheduler.py`, `tcbot/database/base/jobs.py`, `tcbot/database/schema/seed.sql`, `alembic/versions/0007_scheduled_job_owner.py`): the `retention.sweep` registry job had no caller, so runtime telemetry past its window was never removed. A daily `tcbot.retention_daily` sweep applies the `retention_policies` windows, prunes expired MTProto session state, and records the run in `scheduled_job_runs`.

- **A truncated connect replay is durable** (`tcbot/database/enforcement_db.py`, `tcbot/modules/helper/pipelines/connected_flow.py`, `i18n/en-US/connecting.toml`, `i18n/id-ID/connecting.toml`): a new group whose active ban or mute replay stops at the time budget or list cap now queues an `apply` run for each unreached decision. The worker finishes the enforcement instead of leaving existing members unrestricted until a later join. Behavior changes: the connect warning says the bot retries the remaining restrictions automatically instead of asking for the bot to be re-added.

- **Promotion requests expire** (`tcbot/database/base/rbac.py`, `tcbot/database/queues_db.py`, `tcbot/database/scheduler.py`, `alembic/versions/0005_promotion_request_expiry.py`): a pending request now carries an absolute expiry (`PROMOTION_REQUEST_TTL_DAYS`, default 7), is marked `expired` by the hourly sweep or lazily when a new request is filed, and no longer blocks a fresh request for the same target. Behavior changes: a request nobody decides within the TTL becomes terminal.

- **The user locale cache is shared across processes** (`tcbot/database/cache/singletons.py`, `tcbot/database/settings_db.py`): locale reads use the two-level cache with the generation guard, so a language change in one process invalidates the value in every other process instead of waiting for a process-local TTL.

- **Cache activity has metrics** (`tcbot/utils/metrics.py`, `tcbot/database/cache/twolevel.py`, `tcbot/database/cache/redis_io.py`): L1/L2 hits, misses, invalidations, dropped mutations, queue depth, and Redis availability are exposed through the optional Prometheus endpoint, and the same counters are available in-process for diagnostics.

- **MTProto member harvest resumes** (`tcbot/database/mtproto.py`): the cursor is stored under the shared session namespace, a slice stops at the time budget or a flood wait with the cursor intact, and the next slice continues from that position instead of restarting the group.

- **Proof optional for kick, mute, and warn is archived** (`tcbot/database/moderation_db.py`, `kicks_db.py`, `mutes_db.py`, `warns_db.py`, the kick/mute/warn flows): the landed items are linked to the decision as a non-required evidence batch, so an optional proof is not only a channel message.

- **Review-card edits have a durable outbox** (`tcbot/database/base/moderation.py`, `tcbot/database/notifications_db.py`, `tcbot/notification_worker.py`, `tcbot/database/scheduler.py`): a card edit that fails during an appeal approval or a manual unban is retried by the scheduler, so a settled card cannot keep looking decidable.

- **A mute keeps the duration the moderator requested** (`tcbot/database/mutes_db.py`, `documents.py`): the requested duration is stored beside the remaining lifetime, so the history can distinguish the request from a later supersede.

- **Durable unban, appeal, and kick-repair delivery** (`tcbot/database/enforcement_db.py`, `tcbot/database/bans_db/_writes.py`, `tcbot/enforcement_worker.py`, `tcbot/modules/helper/pipelines/unban_flow.py`, `tcbot/modules/helper/pipelines/appeal_review_flow.py`, `tcbot/modules/helper/pipelines/kick_flow.py`): a manual unban and an approved appeal now record the decision and its per-group delivery run in one transaction, and a kick whose post-ban unban still fails queues a reconcile run. The scheduled worker retries unfinished targets, so a partial delivery no longer disappears with the revoked ban record. Behavior changes: a partial unban reports the failed groups and is retried automatically; a stranded kick is repaired without a new kick.

- **Every proof item is archived with its real media type** (`tcbot/modules/helper/pipelines/proof_flow.py`, `tcbot/database/moderation_db.py`, `tcbot/database/bans_db/_writes.py`, `tcbot/modules/helper/pipelines/ban_flow.py`, `tcbot/modules/helper/pipelines/warn_flow.py`): the uploader returns one result per landed message, and the evidence batch stores the item order, media type, archive message id, and file metadata. A gallery that lost a file is a partial batch instead of a single photo. Behavior changes: a manual ban is not filed from an incomplete proof upload, so the moderator resends the evidence; an automated threshold ban may still stand on partial optional evidence.

- **Configured destinations are registered at startup** (`tcbot/database/groups_db.py`, `tcbot/__main__.py`): the proof, log, and appeal destinations now get a `telegram_chats` identity row when they do not have one. Evidence uploads and enforcement targets reference that table, so a fresh deployment no longer fails its first ban on an unregistered proof channel.

- **Expiry revokes now have a consumer** (`tcbot/enforcement_worker.py`, `tcbot/database/enforcement_db.py`, `tcbot/database/scheduler.py`): the expiry sweep queued a revoke run for every managed group but no code read the queue, so an expired restriction stayed in Telegram. The worker claims queued runs, lifts the ban or mute, records each attempt, and retries a failed target up to three times. Behavior changes: an expired decision is enforced on Telegram without a manual unban.

- **pg_cron can own the database-only maintenance** (`tcbot/database/pg_cron.py`, `tcbot/database/scheduler.py`, `config.env.example`): when `PG_CRON_ENABLED` is true and the extension exists, PostgreSQL runs moderation expiry, role expiry, and stuck-enforcement reconciliation every 5 or 10 minutes. APScheduler drops its expiry schedule, so only one owner runs it, and keeps the jobs that need Python or Telegram. Without the extension the bot logs a warning and keeps APScheduler. Behavior changes: expiry survives a dead bot process when pg_cron is enabled.

- **The listener interface is configurable** (`tcbot/__init__.py`, `tcbot/alive.py`, `config.env.example`): `BIND_HOST` selects the interface for the keep-alive and webhook server. The default remains `0.0.0.0`; `127.0.0.1` is available behind a local reverse proxy. Behavior changes: none unless the setting is used.

- **Account erasure has an operator entry point** (`tcbot/database/erasure_db.py`, `tcbot/modules/maintenance.py`, `tcbot/database/scheduler.py`): the erasure queue had a sweeper but nothing could enqueue a request. `/tcforget <user_id> <reason>` now queues one, and the cleanup sweep invalidates the erased user's name and role caches after anonymising the row. Behavior changes: a Founder can erase an account without manual SQL.

- **Speedtest has a full mode** (`tcbot/modules/netspeed.py`, `i18n/*/netspeed.toml`): `/speedtest full` moves a larger sample over four connections per direction and gets a 300 s ceiling. The quick mode keeps its small payload so it does not starve Telegram traffic. Behavior changes: the full mode reports a more representative throughput at the cost of bandwidth.

- **Cache queue evictions are counted** (`tcbot/utils/metrics.py`, `tcbot/database/cache/redis_io.py`): when a revocation needs room at the hard queue ceiling, the evicted display hint is recorded as `tcbot_cache_queue_evictions_total{prefix}`, so an operator can distinguish that case from a dropped mutation.

### Fixed

- **A delivery summary counts a requested group that never got a target** (`tcbot/database/enforcement_db.py`, `tcbot/modules/helper/pipelines/unban_flow.py`): the queue only records an active connected chat, so a group disconnected during the proof window produced no target row, and the summary counted only the rows it had. A ban then read as a complete delivery while that group was never touched. The caller's requested scope is now the floor of the reported total, the shortfall counts as pending, and the unban wording reports it as queued. Behavior changes: a delivery that cannot reach a group that left the federation reads as pending instead of full.

- **A re-queued enforcement run clears its completion stamp** (`tcbot/database/enforcement_db.py`): a run that closed after a failed target kept `finished_at` when the retry deadline returned it to the queue, so the ledger carried a completion time for work that had not started. The requeue clears the stamp.

- **An erased account cannot re-enter the cache during the sweep** (`tcbot/database/scheduler.py`): the name and role caches were invalidated inside the erasure transaction, before its commit, so a concurrent miss could repopulate the pre-erasure row. The ids are returned from the transaction and invalidated after the commit. Behavior changes: none for a successful erasure; a concurrent read no longer restores the erased name.

- **A scheduler job-store failure reports its own cause at boot** (`tcbot/database/scheduler.py`): the store was built before the guarded block, so a missing privilege or an unreachable host raised outside it, left the readiness event unset, and made `start()` wait the full 30 s budget before reporting a generic timeout. The construction now runs inside the guarded block, and the original exception becomes the cause of the reported failure.

- **A server-side SQL refusal does not open the database circuit** (`tcbot/database/engine.py`): psycopg 3 reports a lock timeout, a deadlock, a serialisation failure, or a statement cancellation as an `OperationalError`, and the classifier counted five of them as a link outage, rejecting every database call federation-wide. Those SQLSTATEs prove the link is healthy now and are not counted.

- **The MTProto harvest cursor uses the shared database boundary** (`tcbot/database/mtproto.py`): the cursor read and write bypassed `db_call`, so a stalled database held the harvest for the driver's socket timeout with no circuit accounting. Both run through the shared call budget and breaker now.

- **A delayed apply does not enforce a decision past its deadline** (`tcbot/enforcement_worker.py`): the worker treated every `apply` run whose stored status was still `active` as enforceable, so a run that waited in the queue while a timed ban or mute expired still banned or muted the target. The worker now cancels an apply run whose deadline passed before it claims any group. Behavior changes: a delayed delivery of an elapsed decision is abandoned instead of applied; the revoke path still lifts anything that landed earlier.

- **A timed ban stops being active at its deadline in the single-record read** (`tcbot/database/bans_db/_compose.py`, `tcbot/database/bans_db/_lifecycle.py`): `get_ban` derived `is_active` from the stored status alone, so a timed ban that passed its deadline still read as active until the daily sweep moved the row. An appeal could be filed and a review card decided for a restriction nobody could enforce. The document now applies the deadline at read time, and appeal approval refuses a ban that is no longer in force. Behavior changes: a ban past its deadline is reported inactive immediately, and its appeal cannot be accepted before the sweep runs.

- **A re-ban from a stale record supersedes the live ban** (`tcbot/database/bans_db/_writes.py`): a re-ban that read the active record before another re-ban landed tried to supersede the already superseded row, and the schema rejected the whole decision after its proof was uploaded. The write now supersedes the ban that is active inside the transaction, and a unique-race retry applies the same rule; a record whose deadline passed during the proof window is expired by the insert and the decision stands on its own. Behavior changes: a re-ban that races another re-ban is filed on top of the newer decision instead of failing.

- **An animated proof stays an animation** (`tcbot/modules/helper/pipelines/proof_flow.py`): a GIF was classified as a document and uploaded with `send_document`, while the evidence row recorded `animation`, so the archive and the stored media disagreed. Animations now upload with `send_animation`, and a gallery keeps the animation beside its photos and videos. Behavior changes: a GIF proof lands as an animation message instead of a file attachment.

- **A re-ban keeps the whole previous evidence batch** (`tcbot/database/moderation_db.py`, `tcbot/database/bans_db/_writes.py`): a re-ban without a newly landed proof re-archived only the first previous message as one photo, dropping the other items and their media types. The update now copies every archived item with its expected count, and a partial previous batch stays partial instead of being recorded as complete. Behavior changes: a manual re-ban cannot attach an incomplete inherited proof, so the moderator supplies a complete one.

### Changed

- **The schema pins the definer search path to its own schema** (`tcbot/database/schema/functions.sql`, `alembic/versions/0010_schema_hardening.py`): six `SECURITY DEFINER` functions named `public` in their search path instead of the schema the files were applied to, and the erasure batch read its rows by timestamp alone. The functions now pin `pg_catalog` and the active schema, the batch tie-breaks on `id` like the caller's pre-read, and revision 0010 reapplies the files on an existing database. Behavior changes: none for the deployment schema; a development or test schema no longer resolves a definer function through `public`.

- **The migration takes the schema the bot will read** (`tcbot/database/migrations.py`, `alembic/env.py`, `tcbot/database/engine.py`): `upgrade_head` derived the target schema from `DB_SCHEMA` in the process environment, while the engine used `cfg.db_schema`. A caller that set the schema programmatically could migrate one schema and read another. The caller now passes the schema through the Alembic config, and the environment remains the fallback for a hand-run `alembic upgrade`. Behavior changes: none for a deployment configured through the environment.

- **The migration helper refuses a schema name it cannot quote** (`tcbot/database/migrations.py`): `ensure_schema` interpolated the name into `CREATE SCHEMA`, relying on every caller to validate it. The helper now checks for a plain identifier itself. Behavior changes: an invalid name raises before the statement reaches the server.

- **Integer coercion of database and report values has one owner** (`tcbot/database/types.py`, `tcbot/enforcement_worker.py`, `tcbot/notification_worker.py`, `tcbot/modules/maintenance.py`, `tcbot/database/enforcement_db.py`): the enforcement worker, the notification worker, the repair command, and the run report each converted untrusted integer values with their own copy of the same rules. `database.types.as_int()` now owns the conversion, so a row read through any layer resolves the same way. Behavior changes: none; the accepted values and the fallback are unchanged.

- **A cancelled enforcement run keeps the reason it was abandoned** (`tcbot/database/enforcement_db.py`): the cancellation helper accepted a reason and then discarded it, so an operator found a terminal run with no explanation. The reason is now stored in the run metadata and remains available for diagnosis. Behavior changes: a cancelled run carries `cancel_reason` in its metadata; the enforcement itself is unchanged.

- **A join-time federation ban now reports the full identity and reaches the target** (`tcbot/modules/greeting.py`, `tcbot/modules/helper/keyboards/ban.py`, `i18n/en-US/greeting.toml`, `i18n/id-ID/greeting.toml`): the group notice names the user ID, first name, last name, username, and ban ID, with `View Log` and `View Proof` on the first button row and `Submit Appeal` below. The same links are sent to the banned user as a separate DM with different wording and the ban reason. The notice is posted in every connected group, not only the primary group. Behavior changes: secondary groups receive the ban notice, and a join-time ban now attempts a DM to the target; a user who has blocked the bot or never started it simply receives no DM.

- **The proof destination is deployment configuration** (`tcbot/__init__.py`, `config.env.example`, `README.md`, `docs/getting-started/setup.md`): the loader carried a community channel ID as the fallback for `PROOFS`, so a fresh clone would upload evidence to a chat it did not own. `PROOFS` is required now and boot refuses a missing or invalid value with a clear error. Behavior changes: a deployment that relied on the removed default must set `PROOFS` to its own proof chat before upgrading.

- **A failed kick is recorded as failed, not completed** (`tcbot/database/kicks_db.py`, `tcbot/modules/helper/pipelines/kick_flow.py`, `tcbot/enforcement_worker.py`, `alembic/versions/0008_kick_failed_status.py`): the audit row is written before enforcement, so it started `completed` even when the ban or its follow-up unban never landed. The decision now moves to `failed` on either failure, and the durable reconcile run restores `completed` only after the unban succeeds. Behavior changes: `/check` history marks a stranded kick and the database distinguishes it from a delivered one.

- **The community default locale reaches the render path** (`tcbot/utils/i18n.py`, `tcbot/modules/helper/locale.py`, `tcbot/database/settings_db.py`, `tcbot/database/cache/singletons.py`): `community_settings.default_locale` was resolved by the SQL settings view but never read by the bot, so changing it had no effect. The resolver now falls back to it after the chat-specific preference and before `en-US`, through a shared two-level cache, and reads it only when the specific preference is absent or unknown. Behavior changes: a deployment that sets the column now renders the default language for chats without their own preference; the shipped `NULL` value leaves the behaviour unchanged.

- **An unmute is one decision with a durable delivery** (`tcbot/database/mutes_db.py`, `tcbot/modules/helper/pipelines/mute_flow.py`, `i18n/en-US/muting.toml`, `i18n/id-ID/muting.toml`): revoking the active mute and queueing its per-group `revoke` run now commit together. A partial restore keeps the groups that did not answer in the ledger, and the scheduled worker retries them instead of asking the moderator to run `/tcunmute` again. A run that has not settled yet is reported as queued. Behavior changes: a partially restored unmute is retried automatically.

- **A late delivery cannot undo a newer decision** (`tcbot/database/enforcement_db.py`, `tcbot/enforcement_worker.py`): a queued unban or unmute outlived the decision it belonged to, so a re-ban or a fresh mute before the retry could be lifted by the older run; a delayed kick repair had the same effect on a federation ban. Each run now reads the conflicting decisions in the same query as its action and cancels itself instead of applying the stale delivery. Behavior changes: a newer ban or mute is not lifted by an older retry or by a kick repair.

- **Appeal rejection is one database decision** (`tcbot/database/bans_db/_lifecycle.py`, `tcbot/modules/helper/pipelines/appeal_review_flow.py`): recording the rejection and releasing the review slot now commit together. A former split could record the rejection while the card kept the slot, so the user could not appeal again until the stale window passed. Behavior changes: a rejection that cannot free its slot is not recorded, and a failed card edit is queued for the notification worker.

- **An expired ban withdraws its pending appeal** (`tcbot/database/schema/functions.sql`): automatic expiry now withdraws the pending appeal and drops the review slot in the same statement as the ban status change. A pending appeal left behind can never be decided, because a decision requires an active ban, and it kept a review card alive for a question that no longer exists. Behavior changes: an expired ban leaves no pending appeal or live review slot.

- **A group language change reaches every process** (`tcbot/database/groups_db.py`, `tcbot/database/cache/singletons.py`): the group locale read now uses the shared two-level cache with the generation guard, like the user locale. Behavior changes: a group language change in one process is visible in every other process at once instead of after a process-local TTL of up to 300 s.

- **An enforcement retry skips a disconnected chat** (`tcbot/database/enforcement_db.py`): a failed target whose chat is no longer active is not claimed for another attempt. The database refuses a retry against an inactive chat, so the old claim turned one stale target into a repeating worker failure. Behavior changes: such a target stays failed for operator review instead of being retried forever.

- **Appeal approval is one database decision** (`tcbot/database/bans_db/_writes.py`, `tcbot/modules/helper/pipelines/appeal_review_flow.py`): accepting the appeal, revoking the ban, releasing the review slot, and queueing the unban run now commit together. A former split could leave an accepted appeal beside an active ban, or a revoked ban beside a pending appeal.

- **A manual unban queues its review-card edit atomically** (`tcbot/database/bans_db/_lifecycle.py`, `tcbot/modules/helper/pipelines/unban_flow.py`): the edit is part of the revocation transaction, so a crash after the commit cannot leave a live-looking appeal card over a revoked ban. Behavior changes: the card is closed by the notification worker even when the process stops before the direct edit.

- **Scheduled job ownership is explicit** (`tcbot/database/base/jobs.py`, `tcbot/database/pg_cron.py`, `tcbot/database/schema/functions.sql`, `alembic/versions/0007_scheduled_job_owner.py`): the drift report compared every registry row with `cron.job`, so application-owned jobs were reported as missing when pg_cron was active. `scheduled_jobs.job_owner` separates the pg_cron rows, and the drift audit now runs under pg_cron.

- **Ownership transfer is one atomic decision** (`tcbot/database/users_roles.py`, `tcbot/modules/helper/pipelines/transfer_flow.py`, `i18n/en-US/admins.toml`, `i18n/id-ID/admins.toml`): the owner swap and the previous Founder's Admin grant now commit together under the transfer lock, and the helper re-reads the current owner so a stale prompt cannot replace a newer one. A failed grant no longer leaves the previous Founder without a role; the partial-success warning is gone with the split.

- **The schema splitter handles PostgreSQL escape syntax** (`tcbot/database/schema/loader.py`): quoted strings, `E'...'` backslash escapes, and nested block comments no longer break the statement boundary. Behavior changes: none for the current schema; a future definition using those forms is applied correctly.

- **Unban reports names of failed groups** (`tcbot/modules/helper/pipelines/unban_flow.py`): the summary reads the per-group run report instead of counting a one-shot fan-out. A group that is still being retried is reported as queued rather than as a completed unban.

- **Mute summary names the groups that missed the restriction** (`tcbot/modules/helper/pipelines/mute_flow.py`): a partial mute now appends the failed group titles instead of only showing `done/total`.

- **Appeal deep links accept the full reference range** (`tcbot/modules/appeals.py`, `tcbot/modules/helper/pipelines/appeal_submit_flow.py`): the start filter uses the same 10-to-32 character pattern as the parser, so a legacy reference no longer produces a dead link.

- **Demote messages name the unban and appeal context** (`tcbot/modules/helper/pipelines/demote_flow.py`): a staff member demoted before a manual unban or an approved appeal now receives wording for that decision instead of the generic manual-demote text.

- **Migration runs are serialised across instances** (`tcbot/database/migrations.py`): two instances that boot together could apply the same revision concurrently and the loser crash-looped on a duplicate-object error. The upgrade now runs under a PostgreSQL advisory lock with a bounded connect timeout, so the second instance finds the schema at head.

- **Worker-thread error records reach the error channel** (`tcbot/error_reporter.py`, `tests/test_error_reporter_dedupe.py`): a log record emitted from the Flask webhook thread had no running loop, so the delivery task was dropped and webhook enqueue failures stayed console-only. The reporter remembers the loop it was attached on and hands those records to it; the shutdown drain waits for them with a bound.

- **The shared rules have one owner** (`tcbot/database/moderation_db.py`, `tcbot/database/mutes_db.py`, `tcbot/database/bans_db/_writes.py`, `tcbot/utils/update_processor.py`, `tcbot/modules/helper/scope.py`, `tcbot/database/documents.py`, `tcbot/database/schema/loader.py`): the remaining-lifetime calculation and the conversation key were implemented twice, and the schema loader and documents module carried an unused statement builder and a stale role vocabulary that contradicted `users_roles.RoleName`. Each rule now has one implementation, and the unreferenced copies are gone. Behavior changes: none.

- **The membership cache is written during MTProto harvest** (`tcbot/database/users_cache.py`, `tcbot/database/mtproto.py`): `chat_members` had readers, a retention sweep, and a view but no writer, so the community directory was always empty. The member harvest now records the group membership alongside the identity. Behavior changes: the daily stale-membership cleanup has rows to remove.

- **Every moderation decision owns a case that closes with it** (`tcbot/database/moderation_db.py`, `tcbot/database/bans_db/_writes.py`, `tcbot/database/warns_db.py`, `tcbot/database/mutes_db.py`, `tcbot/database/kicks_db.py`): the investigation that holds a decision was opened with the decision and never closed, so the next decision about the same user reused it and the history of the community collapsed into one case per user. The case now closes with the decision that opened it, every incident owns one case, and a re-ban opens its own. Behavior changes: the case of a decision is `resolved` once the decision is filed, and each incident has its own case.

- **The shared write path of the moderation decisions has one owner** (`tcbot/database/moderation_db.py`): opening the case, archiving the proof of the decision, and closing the case were written four times, once per decision kind, and the copies had already drifted. The three steps now live in one module, so the ban, mute, warning, and kick paths cannot disagree about the case lifecycle or the evidence batch. Behavior changes: none; the decisions themselves are unchanged.

- **The schema the bot works in is configuration** (`tcbot/__init__.py`, `tcbot/database/engine.py`, `alembic/env.py`, `config.env.example`, `AGENTS.md`): the schema of the application was hardcoded to `public`, so a developer working against a shared server had no way to keep its work out of the deployment. `DB_SCHEMA` names the schema now, and it defaults to `public`, so a deployment that does not configure it is unchanged. The project uses three schemas and no more: `public` for the deployment, `test` for the integration tests, and `development` for a developer. A schema that does not exist yet is created before the migrations run, so a fresh database comes up empty. Behavior changes: none; the default schema is unchanged.

- **The connection pool is configuration** (`tcbot/__init__.py`, `tcbot/database/engine.py`, `config.env.example`): the pool carried a fixed capacity of twenty connections plus ten overflow, which is larger than most hosted PostgreSQL plans grant, and an oversized pool does not fail at startup: it fails later as a "max clients reached" refusal on every call that needs a connection, and the circuit breaker reads that refusal as an outage of the database. `DB_POOL_SIZE` and `DB_MAX_OVERFLOW` name the capacity now. Behavior changes: the default pool shrank from thirty connections to ten, so a deployment that relies on the old capacity has to set the two variables.
